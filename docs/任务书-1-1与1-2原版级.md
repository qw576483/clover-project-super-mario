## 6. ★★★ 开工方式：**批次流水线**（skill §1.13 四拍，逐字照做）

> **为什么不"改一处编译一次 / 改一处截一次图"**：编译是**分钟级**，
> 进 Play + 注入按键 + 抢拍也是**分钟级 ×N**，而读数据 / 跑断言 / 数据 diff 是**秒级**。
> 改一处就截图 = 把最贵的动作重复 N 次（实测量级：改 30 处 ⇒ 30 次分钟级等待，其中 29 次纯重复）。
> **便宜的多跑，贵的攒一批只做一次。**

| 拍 | 做什么 | 禁令 |
|---|---|---|
| **① 一次性取证**（只读） | 把依据一次查完（原版数据 / 引擎 API 出处 / 现有代码现状），产出**改动清单**：改哪几个文件、每处改什么、**每处的判据是什么** | ⛔ 这一拍不许写代码 |
| **② 批量改** | 按清单把改动**一次全写完** | ⛔ 不编译、不截图；⛔ 不许改一处编译一次 |
| **③ 一次编译 + 预演** | 编译**一次**并确认成功（`compilationFailed: false`）→ 跑**廉价自检**（离线断言 / 数值探针 / 数据 diff / 静态检查）→ 一轮预演里挑出的问题**批量修** → 再预演一轮。**循环粒度 = 一轮预演** | 编译失败 ⇒ ⛔ 不许测 |
| **④ 集中出证据**（只做一次） | 把要实机画面的项排成**一张执行清单**：**一条驱动链路按序跑完所有项 + 按点截图**，截完统一做同机位比对 | ④ 之后再改代码 ⇒ 只重采**受影响的行** |

**③ 必须产出「预演报告」**：逐项写清哪些「已就绪、可截图」、哪些仍有风险 —— ④ 一次采对，避免"采完才发现要改"。

**四条硬不变量（一条不许丢）**：
1. **任何实测之前，编译必须已成功**；编译失败 ⇒ 中止一切验证（否则测的是旧程序集）。
2. **证据必须比代码新，口径按批次**：④ 之后若又改代码 ⇒ **只作废受影响的行**，不推倒全部重采。
3. **日志里的 Error / NullReference 当批次清零**（修掉或登记为已知 + 给出处）。
4. **收尾统计"错误总数"**，不是"我没引入新错"。

**「交付单元」定义不变**：能被一条命令判生死的那一级（一个功能 / 一个面板），**不是"一行代码"**；
单元内部可以批量，⛔ **单元之间不许跳过 ③④**。
